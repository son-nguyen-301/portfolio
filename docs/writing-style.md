# Writing style

Every word on the site, in the docs, in commit messages and in pull requests follows these rules. Many readers are not engineers, and many read English as a second language.

## The main rule

Write plain and simple. Go straight to the point. If a simpler way to say it exists, use it.

## Rules

1. Say the main point first. Add details after, only if needed.
2. Short sentences. One idea per sentence.
3. Common, everyday words. If a 12-year-old would not know the word, pick another one.
4. No fancy words, wordplay, jokes, puns, idioms or metaphors.
5. Use a technical term only when it is the real name of the thing (`Nuxt`, `Playwright`, `Claude Code`).
6. Say who does what: "I fixed the bug", not "The bug was fixed".
7. Be direct.
8. No filler. No "I hope you are well", no "Let me know if you have any questions".
9. Don't repeat a point in different words.
10. Keep it short. Stop when the point is made.
11. Use a list for steps or several items. Otherwise write normal sentences.
12. No emoji.

## Words to swap

| Don't write | Write |
| --- | --- |
| utilize, leverage | use |
| facilitate | help |
| implement | build, add |
| in order to | to |
| due to the fact that | because |
| prior to | before |
| subsequently | then, after that |
| additionally, furthermore, moreover | also |
| however | but |
| approximately | about |
| numerous | many |
| robust, seamless, streamlined | say what it does |
| delve into, dive deep into | look at |

## On the site

- Case studies are written by Son, in the first person: "I built", "I chose".
- Buttons say what happens: "Book a 30-minute call", "Copy email", "Message me on Upwork".
- Numbers keep their real precision. Don't round "419,729 bytes" into "about half a megabyte" unless the label says "about".
